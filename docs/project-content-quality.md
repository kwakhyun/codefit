# 저장소 학습 콘텐츠 검증

공개 저장소의 프로젝트 점검, 코드 이해 훈련, 서비스 동작 실습은 수집한 커밋의 정적 코드에 근거한다. 실제 서비스 실행이나 저장소 전체의 동작을 인증하지 않는다.

## 수집과 생성

- 문서, 검증 스크립트, 로딩 화면과 장식 컴포넌트보다 실행 코드와 도메인 처리를 우선한다. 후보가 적은 프로젝트에서는 화면 구현도 수집한다.
- 최초 8개 파일에서 확인한 import를 두 차례 따라가며 최대 16개 파일을 읽는다. 후속 수집은 매회 최대 3개 슬롯을 의존 파일에 쓰고, 남은 슬롯으로 독립적인 실행 경계도 살핀다. PR은 변경된 줄 주변으로 범위를 제한한다.
- 파일별 발췌와 전체 컨텍스트 크기는 제한한다. 짧은 함수의 앞선 반환 조건과 뒤쪽 분기가 함께 남도록 수집한다. JS/TS 파일의 여러 줄 조건식은 문자열과 주석을 구분해 하나의 묶음으로 다루며, 헤더와 PR 변경 줄에도 같은 예산 처리를 적용한다. PR은 변경된 표현식에 먼저 예산을 쓰고 주변 문맥을 추가한다. 묶음이 예산을 넘으면 일부 줄만 남기지 않고 제외한다. 전체 컨텍스트를 줄일 때는 import와 타입 선언보다 실행 조건을 우선한다. 이 과정은 코드를 실행하거나 완전한 구문 분석을 하지 않으므로 모든 표현식과 호출 관계의 보존을 보장하지 않는다.
- 서버가 발급한 근거 ID를 실제 코드로 복원하고, 인용과 선택지 형식을 검증한다. 선택지는 공백과 유니코드 표기를 정규화하여 중복을 검사한다.

## 저장 전 품질 검사

생성 요청과 별도의 모델 요청으로 새 콘텐츠를 검토한다. 실습 정답 인덱스를 제공하지 않고 검토 모델이 선택지를 다시 판정하게 한다. 정확히 한 선택지를 지지하며 생성된 정답과 일치해야 통과한다.

검토 대상은 잘못된 단정, 결정적 근거 누락, 복수 정답, 답안 공개 전 문구의 정답 노출, 반복 시나리오, 사용자 행동과 관찰 결과가 없는 서비스 실습이다. 해설은 답안 공개 후 제공되므로 정답 노출 검사와 구분한다. 프로젝트 점검의 열린 설계 질문과 향후 검증 계획은 구현 사실을 단정하는 문장과 구분한다.

실습의 제목, 목적, 용어 설명, 읽는 순서와 가정은 살펴볼 조건을 안내하고 결과는 알려주지 않도록 생성한다. 호출 횟수를 묻는 문항에서 특정 횟수의 호출이 모두 성공한다고 전제하거나, 호출 여부를 묻는 문항에서 그 호출이 이미 성공했다고 가정하는 경우도 정답 노출로 본다. 검토 모델은 사실 관계 판정과 별도로 노출 문구를 원문 그대로 인용해야 하며, 서버는 답안 제출 전에 보이는 문구에 실제로 포함되는지 확인한다. 서비스 실습은 내부 설정값이나 함수 반환값만 묻는 문항과 사용자 행동 뒤의 관찰 가능한 결과를 구분해 판정한다.

주변 코드는 앞선 반환 조건이나 이후 실패 처리 등 모순을 찾는 데만 쓴다. 학습자에게 보여 주지 않은 주변 코드로 정답의 근거 부족을 보충하지 않는다. 특정 저장 명령의 결과만으로 이후 처리까지 포함한 최종 저장 상태를 보장하지 않는다. 모든 문항의 검토 ID가 정확히 한 번 반환되어야 한다.

품질 문제를 찾으면 지적 사항과 이전 초안으로 한 번 수정하고 다시 검사한다. 지적되지 않은 문항은 서버에서 원문 그대로 유지해, 수정 과정에서 새로운 문제가 생기는 범위를 줄인다. 요청 취소와 최대 105초의 생성 제한은 수정 요청에도 이어진다. 재검사 실패, 시간 초과, 잘못된 응답이 발생하면 미검증 초안을 반환하거나 저장하지 않는다. 이미 완료된 학습 단계는 기존 저장 절차에 따라 유지한다. 추가 검토와 수정은 API 비용과 응답 시간을 늘린다.

코드/서비스 실습의 수정 응답은 기존 배열 길이와 인덱스를 유지하되, 지적되지 않은 슬롯은 `null`로 생략할 수 있다. 서버가 이 슬롯을 원문으로 복원하므로 불필요한 재출력을 줄인다. 지적된 슬롯은 완성된 수정 문항이 필요하며, 누락이나 잘못된 근거는 거절한다. 병합한 전체 문항에 형식 검사와 독립 품질 검사를 다시 적용한다.

모델 검토도 오판할 수 있으므로 통과율은 정답률이나 모든 저장소에 대한 보증이 아니다. 원문과 생성 결과의 표본 검토를 함께 수행해야 한다. 기존에 저장된 학습 기록은 자동으로 재생성하지 않는다.

## 재현 가능한 유료 검증

아래 명령은 DB에 쓰지 않으며, 보고서는 Git에서 제외된 `artifacts/` 아래에만 저장한다. `--live`가 없으면 API를 호출하지 않는다.

```sh
node --env-file=.env.local --import tsx scripts/evaluate-project-content.ts \
  --live --url https://github.com/OWNER/REPO \
  --out artifacts/project-content/result.json
```

기본 실행 범위는 프로젝트 점검(`analysis`), 코드 이해(`code`), 서비스 동작(`service`), 현재 AI 활용(`observed`), 새로운 활용 제안(`proposed`)이다. 모두 실제 운영 생성 함수와 저장 전 품질 검사를 사용한다. DB 저장이나 서비스 이용 횟수 차감은 하지 않는다.

움직이는 기본 브랜치 대신 저장된 보고서의 소스 스냅샷으로 재생성할 수 있다.

```sh
node --env-file=.env.local --import tsx scripts/evaluate-project-content.ts \
  --live --snapshot artifacts/project-content/result.json \
  --out artifacts/project-content/recheck.json
```

영향받은 단계만 다시 확인할 때는 `--stages`에 쉼표로 구분해 지정한다. 아래 예시는 저장된 `analysis`를 재사용하고 AI 활용 학습 두 단계만 새로 생성한다. 미선택 선행 단계가 보고서에 없으면 추가 유료 호출 없이 해당 단계를 건너뛰고 이유를 남긴다.

```sh
node --env-file=.env.local --import tsx scripts/evaluate-project-content.ts \
  --live --snapshot artifacts/project-content/result.json \
  --stages observed,proposed \
  --out artifacts/project-content/workshop-recheck.json
```

`service`에는 `analysis`와 `code`가, `proposed`에는 `analysis`와 `observed`가 필요하다. 코드 생성이 실패해도 독립적인 AI 활용 단계는 계속 검증한다. 선택한 단계가 실패하면 이전 보고서의 결과로 대체하지 않으며, 의존 단계는 `skipped`로 기록한다. 재사용한 선행 결과는 `reused`로 표시해 새 검증과 구분한다. 선택한 단계가 모두 통과하지 않으면 종료 코드 1을 반환한다.

각 단계에는 동일한 `requestId` 아래 생성, 독립 심사, 한 차례 수정과 재심사, TypeSafe 호출을 모두 기록한다. `runs`에는 모델, 토큰, 추정 비용과 지연을, `usage`에는 단계별/전체 합계를 담는다. 가격을 모르는 모델은 비용을 0으로 간주하지 않고 `unpricedRequests`와 알려진 비용 합계를 따로 남긴다. 병렬 호출 지연 합계와 단계의 실제 소요 시간은 다를 수 있다.

`drafts`는 OpenAI의 성공 응답을 복제해 얻은 JSON 출력만 보관하므로, 최종 결과에서 제거되거나 수정된 초안과 심사 결과도 원문과 비교할 수 있다. 요청 본문, 인증 헤더, 실패한 공급자 응답 본문은 기록하지 않는다. 실패는 안전한 분류와 HTTP 상태로 표시하고, 콘텐츠 품질 오류의 구체적인 지적은 키를 가린 뒤 보존한다. 보고서는 호출 완료 때마다 순차적으로 교체해 중단 전 계측을 남긴다.

개인 프로젝트의 원문, 평가 내용과 보고서는 공개 문서나 테스트 데이터에 복사하지 않는다. `artifacts/`의 실험 원문은 앱 타입 검사에서도 제외한다. 하네스의 단계 선택, 의존 단계 처리, 계측 전달, 오류 정보 보호와 무호출 실행은 모의 테스트로 확인한다.
