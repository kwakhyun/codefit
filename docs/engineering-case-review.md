# 올거나이즈 지원용 엔지니어링 사례 검토

검토일: 2026-09-18. 기준 코드: `48c3bf4`. 이 문서는 제출용 PDF가 아니라 사례 선택과 사실 확인을 위한 자료다.

[AI Native Back-end Engineer 공고](https://career.rememberapp.co.kr/job/posting/338272)는 LLM 특성을 고려한 서버 설계, AI 시스템의 제품화, 데이터베이스 이해, 보안과 지연 및 비용의 균형을 요구한다. 따라서 기능 개수나 화면 디자인보다 아래 두 사례를 중심으로 기술서를 구성하는 것이 적합하다. 공고의 대규모 문서 처리, RAG 및 온프레미스 운영을 Codefit에서 수행한 것으로 표현하지 않는다.

## 우선순위 1: 만료된 AI 실행의 늦은 응답으로부터 결과와 사용량 보호

### 질문 1. 어떤 문제가 있었는가?

AI 요청이 오래 걸려 작업이 만료된 뒤 같은 요청 ID를 재획득할 수 있었다. 하지만 이전 실행의 실패 정리가 ID만으로 새 진행 작업을 삭제했고, 늦은 성공도 새 결과를 변경할 수 있었다. 요청 ID를 저장했다는 사실만으로 멱등성이 완성되지 않은 것이다. 문제, 제출 기록과 생성 사용량이 서로 다른 상태로 남을 위험도 있었다.

이는 운영 고객 장애 통계가 아니라 기준 커밋 `1eeefc7`의 저장소에서 순서를 통제해 재현한 결함이다. [원본 재현](../reports/concurrency-baseline.json)에 `lateFailureDeletedNewExecution: true`가 남아 있다.

### 질문 2. 어떻게 풀었는가?

1. 논리 요청 ID와 실행 소유권을 분리했다. 획득할 때마다 UUID 토큰을 새로 발급하고, 완료/실패/예약 변경 모두 현재 토큰, 소유자, 종류, 상태와 만료를 검사한다.
2. 입력을 정규화한 SHA-256 지문으로 같은 요청의 재시도와 다른 입력의 ID 재사용을 구분한다. 실패해도 지문은 남긴다.
3. 작업 획득은 짧은 트랜잭션으로 끝내고 외부 AI 호출 중에는 DB 잠금을 유지하지 않는다.
4. 생성 결과, 목록용 데이터, 작업 완료와 사용량 확정을 한 트랜잭션으로 묶는다. 검토도 제출/진도/작업 완료를 함께 처리한다.
5. SQLite/PostgreSQL에 같은 계약을 적용하고, 늦은 성공/실패와 최종 UPDATE 실패를 주입해 중복과 부분 저장을 검사한다.

단순 타임아웃 연장은 경합을 늦출 뿐이다. 프로세스 메모리의 잠금으로는 여러 실행 인스턴스를 보호하지 못한다. UUID는 단조 증가 세대 번호가 아니라 현재 실행의 일치 여부를 확인하는 토큰이며, 이를 검사하는 DB 쓰기만 보호한다.

**증거:** [설계와 흐름도](engineering.md#ai-실행-소유권과-원자적-완료), [공통 계약 테스트](../src/lib/server/concurrency-contract.test-helper.ts), [PostgreSQL 트랜잭션](../src/lib/server/postgres-store.ts), [리비전/요청 지문/소유권 검사](../src/lib/server/write-conflicts.ts), [과거 격리 PostgreSQL 검증](../reports/stability-validation.json).

2026-09-14 기록에는 서로 다른 backend PID를 가진 5개 PostgreSQL 연결에서 조건부 갱신 및 완료 요청 중 하나만 성공한 검증이 있다. 이번 검토에서는 SQLite의 관련 3개 계약만 다시 실행해 통과했다. 과거 PostgreSQL 결과를 최신 커밋의 전체 PostgreSQL 검증으로 바꾸어 표현하지 않는다.

**설명해야 할 한계:** DB에 중복 결과가 확정되는 것을 막는 계약이다. 제공자가 처리했지만 응답이 유실된 경우, 재획득/재호출 비용까지 정확히 한 번으로 만들 수는 없다. 외부 호출과 DB를 묶는 분산 트랜잭션은 없다.

## 우선순위 2: 정상 코드를 오답으로 판정하는 LLM 검토의 품질과 비용 결정

### 질문 1. 어떤 문제가 있었는가?

구조화된 JSON을 반환해도 평가 내용은 틀릴 수 있었다. 초기 검토는 정상적인 대체 구현을 거절했고, 프롬프트만 보완한 실험에서도 오판이 남았다. 생성 문제에서도 예제와 참고 정답이 모순되거나 리팩터링 문제에 기능 수정이 필요한 사례가 있었다.

### 질문 2. 어떻게 풀었는가?

1. React, Python, SQL, Unity의 참고 정답, 대체 구현, 오류 코드, 통과를 유도하는 주석을 포함한 16개 사례와 요구사항별 기대값을 준비했다.
2. 초기 지침 → 지침만 변경 → 같은 지침에 medium 추론을 적용한 결과를 보존했다. 전체 통과 여부는 각각 15/16, 14/16, 16/16 일치했다. 프롬프트 수정만으로 해결됐다고 해석하지 않았다.
3. 이후 Luna를 같은 사례에 두 번씩 적용해 32/32 전체 판정, 104/104 요구사항 판정 일치를 확인했다. 기록된 추정 비용은 32회 합계 $0.023385, 지연 중앙값 5.883초였다.
4. 생성은 6개 분야 × 2회 × 3개 모델을 비교했다. JSON 구조 통과와 의미적 품질을 분리하고, TCP 길이 헤더 및 입력 검증 반례를 직접 확인했다. 저렴한 모델과 차이가 미미하다는 근거가 부족해 검토는 Luna, 생성은 Sol로 분리했다.
5. 요구사항 누락/중복을 서버에서 검증하고 점수는 서버가 계산한다. 모델, 지침 버전, 토큰, 지연과 비용 계측을 남기되 사용자 코드 원문은 계측 로그에 보관하지 않는다.

**증거:** [평가 집합](../evals/review-cases.ts), [초기 결과](../reports/ai-evaluation-baseline.json), [지침 변경 결과](../reports/ai-evaluation-prompt-only.json), [추론 변경 결과](../reports/ai-evaluation.json), [Luna 결과](../reports/ai-review-luna.json), [생성 반례](../reports/generation-counterexamples.json), [선택 이유](engineering.md#모델-선택-검토-luna-생성-sol-유지--2026-09-14).

**설명해야 할 한계:** 개발 중 반복 사용한 작은 평가 집합이며 독립적인 평가자/숨겨진 평가 집합이 없다. 32/32를 서비스 전체 정확도 100%로 표현하지 않는다. 과거 Mini와의 요청당 추정 비용 차이는 동시 무작위 비교나 운영 절감률이 아니다. 생성 Sol도 오류와 응답 실패가 있었으며 보편적 우위를 입증하지 않는다. 이번 검토에서는 유료 호출을 반복하지 않았다.

## 제출 구성 제안

제목 예시: **느리고 실패할 수 있는 LLM 호출을 안정적인 서비스 기능으로 만들기**.

서비스 소개는 반 페이지 정도로 제한하고, 두 핵심 사례 각각에 문제 재현 → 원인 → 대안과 선택 → 구현 → 검증 → 남은 한계를 배치한다. 백엔드 경합은 트랜잭션 흐름도와 소유권 조건, AI 품질은 실제 오판 예시와 비교표를 중심으로 설명한다. 나머지 기능은 부록/저장소 링크로 연결한다.

현재 근거로 대규모 트래픽, RAG 검색 품질, 실제 고객 운영 장애, 온프레미스 운영, 학습 효과 향상을 주장할 수는 없다. 지원서의 본인 역할은 실제 수행 범위를 확인해 적으며, AI 코딩 도구의 구현 지원과 본인이 결정·검토한 내용을 구분한다. 기술적으로 설명할 수 없는 설계 결정을 독자적으로 수행한 것으로 쓰지 않는다.

## 이번 검토에서 발견한 CI 결함

[CI 실행 35287683308](https://github.com/kwakhyun/codefit/actions/runs/35287683308)은 typecheck에서 중단됐고 PostgreSQL 및 브라우저 테스트는 실행되지 않았다. 빌드한 로컬에는 `next-env.d.ts`가 있었지만 Git에서 제외된 새 체크아웃에는 없어 PNG/WebP 타입을 찾지 못했다.

커밋을 별도 임시 폴더에 내보내고 `.next`, `next-env.d.ts`, 환경 파일 없이 기존 설치 의존성만 연결해 같은 오류 두 개를 재현했다. `typecheck`를 `next typegen && tsc --noEmit`으로 변경한 뒤 같은 폴더에서 통과했다. 자동 생성 파일을 커밋하거나 무분별한 타입 선언으로 오류를 숨기지 않았다. 이는 로컬 재현/수정 검증이며 원격 CI 재실행 성공을 의미하지 않는다. 비교 로그는 로컬 `artifacts/clean-typecheck-before.log`, `artifacts/clean-typecheck-after.log`에 남겼다.

이 결함은 반드시 고쳐야 할 검증 환경 문제지만, 지원 기술서의 대표 고난도 사례보다 보조적인 품질 관리 사례다.
