# 운영 반영 검토 — 2026-09-20

## 판단

**수정한 제품 변경은 커밋하고 운영 반영하는 것을 권장한다.** 백업 복원 범위, 오래된 프로젝트 접근, 평가 근거 검증과 실험 후 코칭은 실제 사용 흐름을 개선한다. SOTA를 입증하지 못했다는 사실은 이 기능들을 배포하지 않을 이유가 아니다. 다만 변경 전 상태를 통째로 바로 배포하는 것은 권장하지 않는다. 이번 검토에서 호스팅 제한과 맞지 않는 백업 크기를 수정했고, 독립적인 개선이 많이 누적되어 기능별 커밋으로 검토와 되돌리기 범위를 명확히 하는 편이 낫다.

이 문서는 배포 실행 결과가 아니다. 커밋, push, 운영 배포, 운영 DB 읽기·쓰기를 수행하지 않았다.

## 발견해 수정한 문제

### 백업 제한과 Vercel의 요청·응답 제한 불일치

수정 전 앱은 10,000,000바이트를 허용했다. 그러나 Vercel Functions의 요청과 버퍼링된 응답은 4.5 MB로 제한되므로, 로컬에서 유효한 파일이 운영에서 플랫폼 오류로 거절될 수 있었다. [Vercel 공식 제한 문서](https://vercel.com/docs/functions/limitations).

공통 상수를 4,000,000바이트로 조정하고 브라우저 파일 검사, API 파서와 내보내기 직렬화에 같은 값을 적용했다. 안내 문구도 공통 표시 상수 `4 MB`를 사용한다. 정확히 한도까지 허용하고 한 바이트 초과부터 거절하는 경우, UTF-8 한글, 오류 응답과 기존 기록 보존을 검사했다. 일부 기록만 조용히 내보내지 않는다.

이전 로컬 버전에서 만든 4 MB 초과 파일은 웹으로 가져올 수 없다. 이 경우 분할 백업 또는 별도 이관 도구가 필요하다. 이번 수정은 대용량 복원 기능을 추가한 것이 아니다.

### 백업 사전 확인의 순차 조회

문제마다 전체 문제 데이터를 읽어 신규 문제 수를 확인하던 처리를 ID 500개씩 묶은 COUNT 조회로 바꿨다. 최대 2,500개 기준으로 **사전 확인 조회가 최대 2,500회에서 5회**가 된다. 중복 ID와 SQL처럼 생긴 문자열, 두 DB의 매개변수 바인딩을 검증했다. 실제 운영 지연을 측정해 얻은 속도 개선 배수는 아니다.

실제 복원 트랜잭션 안에는 레코드별 쓰기가 남아 있다. 최대 크기 백업의 운영 리전 왕복 지연까지 보장하지는 않으며 대규모 복원 시 추가 측정이 필요하다.

### 화면 문구

- “AI 설명 평가 …단계가 낮은 영역부터”를 현재 영역의 평가와 추천 순서를 구분한 문장으로 바꿨다.
- “같은 계정의 서버 저장 기록을 확인합니다”를 “이 계정에서 실습을 완료하면 다음 질문이 열립니다”로 바꿨다.
- “다른 상황에서도 두 가지 판단을 확인했어요”를 “새로운 상황의 두 문제를 모두 맞혔어요”로 바꿔 실제 결과를 표시한다.
- “첫 제출을 기록합니다”, “최종 평가 요청 1회가 사용됩니다”와 실험 코드 가져오기 버튼 등을 자연스럽게 정리했다.
- 학습 효과를 단정하지 않는 설명, 이전 실습 여부와 외부 도움의 자기 신고라는 구분은 유지했다. 문항 자체와 채점 기준은 바꾸지 않았다.

- 격리 PostgreSQL 18.4, `127.0.0.1:55440`의 새 임시 클러스터에서 관련 계약 **13개 통과**, 무관한 23개는 미선택했다. 운영 DB를 사용하지 않았다.
- 최종 프로덕션 빌드에서 Chromium 브라우저 시나리오 **13개 통과**. 백업 다운로드·계정 전환·복원, 프로젝트 학습과 기록 목록, 평가 근거, 직접 실험과 후속 질문을 확인했다. AI 응답은 모의 응답을 사용했고 새 유료 호출은 없었다.
- 390px 모바일 가로 넘침, 관련 axe 자동 접근성 검사와 결과 화면 스크린샷을 확인했다. 이번 검토에서 Firefox/WebKit을 다시 실행한 것은 아니다. 이전 변경별 검증 기록과 구분한다.
- TypeScript 검사를 포함한 프로덕션 빌드, 이번 수정 파일의 ESLint와 Prettier, `git diff --check` 통과.
- 보고서 42개는 합계 약 2.11 MB다. 변경 파일의 API 토큰·개인 키·비밀번호 포함 DB URL 패턴 검사에서는 `.env.example`의 명시적인 `user:password@host` 예제만 검출됐다. 제한된 패턴 검사이며 모든 민감정보 부재를 보증하지 않는다.

초기 실행에서는 새 경계값 테스트가 기존 기록을 덮어쓰지 않는 `archiveLegacy` 정책 때문에 실패했다. 테스트 fixture만 직접 갱신하도록 수정한 뒤 통과했다. 로컬 서버 실행 권한과 이전 임시 DB 계정 설정 문제는 새 격리 클러스터로 해결했다. 이관 검사를 Node 내장 test runner로 실행한 시도는 runner 불일치로 실패했으며, 올바른 Vitest 실행의 162개 통과에 포함된다. 실패한 준비 시도를 제품 회귀나 성공 사례로 합산하지 않았다.

## 커밋과 배포 순서 권고

1. 실행기 검증과 해당 테스트·문서.
2. 프로젝트 평가, 프로젝트 학습, 기록 목록, 백업과 DB 계약을 함께 묶기. 공유 타입과 백업 검증이 서로 연결되어 있으므로 파일을 무작위로 나누지 않는다.
3. 실험과 후속 코칭, 관련 UI와 HTTP 검증.
4. 원본 평가 보고서, 재검토 스크립트와 검증 문서. 각 기능 커밋에 대응 문서를 포함해도 된다.

이 분할은 권고이며 실제로 각 중간 커밋을 만들거나 빌드해 검증한 결과는 아니다. 최종 조합은 빌드와 위 검사를 통과했다. 런타임 의존성을 새로 추가하지 않았고 DB 변경은 테이블과 인덱스 추가이며 기존 초기화의 트랜잭션 잠금 안에서 적용된다.

운영 반영 시에는 먼저 동일 설정의 프리뷰에서 로그인, 기존 기록 재조회, v2 가져오기와 v3 왕복, 명시적인 AI 질문을 확인한 뒤 승격하는 것이 적절하다. 운영 데이터 규모에서 새 인덱스 생성 시간, 실제 제공자 연결과 최대 복원 시간은 이번 로컬 검증의 범위 밖이다. 과거 배포로 되돌리면 새 v3 가져오기와 새 UI는 사용할 수 없으므로 롤백을 DB 데이터 삭제와 혼동하면 안 된다.

보고서의 합성 사례는 독립 시험 집합이나 사람의 학습 효과 연구가 아니다. `summarize-coach-targeting.ts`는 이전 프롬프트의 고정 비교 자료를 대상으로 하며 현재 프롬프트 해시가 달라지면 의도적으로 중단한다. 이를 현재 버전의 재평가 성공으로 표현하지 않는다. **제품 신뢰성 개선은 배포하고, SOTA 주장은 계속 보류**하는 판단이다.
