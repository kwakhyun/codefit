## 공개 벤치마크 적합성 조사

[공식 TutorBench 설명](https://labs.scale.com/leaderboard/tutorbench)은 전문가가 작성한 STEM 문항으로 설명 조정, 피드백, 힌트를 평가한다. 코드핏의 한국어 프로젝트 설계 평가와 입력·출력·판정 기준이 다르다. 일부 컴퓨터과학 문항만 골라 코드핏용으로 바꿔 검사하더라도 공식 전체 점수나 리더보드 순위로 표현할 수 없다.

[MRBench 논문](https://aclanthology.org/2025.naacl-long.57/)은 수학 학습 대화에 대한 튜터 응답을 교육적 차원에서 평가한다. 오류 식별, 안내와 실행 가능한 피드백이라는 관점은 참고할 수 있지만, 그 정답을 프로젝트 설계 답변의 0~4단계 정답으로 치환할 수 없다.

이번 조사로 코드핏과 동일한 전체 제품 과제를 다루는 공인 순위를 확보하지 못했다. 다른 과제의 API 점수를 얻는 데 추가 비용을 쓰는 대신, 주장할 범위를 좁히고 비교에 필요한 독립 기준을 준비한다. 조사 범위 밖에 적합한 자료가 전혀 없다는 뜻은 아니다.

## 준비된 외부 검토 자료

`npm run eval:prepare-review`를 실행하면 고유한 폴더에 다음 자료를 만든다.

1. `reviewer-a-answers.json`, `reviewer-b-answers.json`: 모델 응답을 보지 않고 12개 답변의 적정 점수와 이유를 작성한다. 독립성 여부와 이해관계를 명시한다.
2. `reviewer-a-responses.json`, `reviewer-b-responses.json`: 앞 파일을 확정한 뒤 제공한다. 모델·버전·비용·개발자 기대 점수를 숨긴 60개 결과의 잘못된 설명과 후속 행동의 구체성을 검토한다. 응답 실패도 포함한다.
3. `coordinator-key.DO-NOT-SHARE.json`: 담당자만 보관하는 모델 대응표다.
4. `manifest.json`: 입력과 자료의 해시를 보관한다. 모델 이름이 있는 경로가 포함되므로 검토자에게 전달하지 않는다.

순서는 검토자별로 무작위로 섞는다. 문체나 내부 문장 번호로 방식을 추측할 가능성이 있어 완전한 눈가림을 보장하지 않는다. 로컬 해시는 사후 변경을 찾기 위한 수단이며 공인 타임스탬프나 외부 사전등록을 대신하지 않는다. 자료는 로컬에 생성했으며 다른 사람에게 보내지 않았다.

이 자료는 **기준을 맞추는 교정용**이다. 독립 검토자가 채점하더라도 이미 개발에 쓴 입력이 미공개 시험 집합으로 바뀌지는 않는다. 현재 모든 사람 평가값은 비어 있다. AI가 대신 채운 값을 사람 평가로 처리하지 않는다.

## 본 비교의 초안

목표 과제는 '한국어 프로젝트 설계 설명의 구체성과 오개념을 평가하고 실행 가능한 다음 확인을 제안하기'로 제한한다. 서비스 전체가 최고라는 주장보다 먼저 이 기능을 검증한다.

### 비교 전 고정할 조건

- 구현에 참여하지 않은 개발·교육 경험자 2명이 새로운 문항과 답변, 판정 기준을 작성한다. 5개 영역을 고르게 포함하고 오개념, 타당한 대안, 부분 설명, 불확실성, 긴 답변, 비개발자의 일상어 표현을 포함한다.
- 우선 새 사례 50개를 탐색적 비교의 제안 규모로 삼는다. 이는 검정력 계산으로 정한 확증 표본 수가 아니다. 이 탐색 결과를 보고 본 실험의 표본 수를 정하면 탐색 사례는 본 검증에서 제외한다.
- 개발자는 시험 문항으로 프롬프트를 조정하지 않는다. 불가피한 수정은 버전을 바꾸고 별도 새 문항에서 평가한다. 각 비교의 코드 해시, 모델·추론 설정, 입력, 최대 출력량, 날짜와 실패 정책을 먼저 기록한다.
- 비교 대상은 코드핏, 같은 Luna에 공통 채점 기준만 제공한 일반 API 구성, 더 강한 모델의 동일 일반 구성이다. API 비교를 ChatGPT 제품 비교라고 부르지 않는다. 더 강한 모델은 호출 전 고정하며 결과를 본 뒤 유리한 모델만 남기지 않는다.
- 모든 구성에 동일한 정보와 기준, 시간·토큰 예산을 준다. 출력 순서를 섞고 모델명을 숨긴다. 호출 오류와 시간 초과를 포함해 모두 기록한다. 같은 사례의 반복 호출은 독립 사례로 세지 않는다.

### 판정과 분석

두 검토자가 먼저 각각 0~4단계 정답과 이유를 정한다. 불일치율을 보고하고, 최초 판단을 보존한 상태에서 제3자 또는 명시적인 합의 절차로 최종 정답을 만든다. 결과를 만든 모델이 자기 결과의 유일한 판정자가 되지 않게 한다.

주요 지표는 사람 판정 대비 절대 점수 오차다. 안전상 중요한 보조 지표는 사람 판정 0~~1인데 시스템이 3~~4를 부여한 비율이다. 피드백의 오개념, 실제 구현에 대한 근거 없는 단정, 구체적 다음 행동, 응답 실패, 토큰 비용과 지연을 따로 보고한다. 응답 실패를 제외한 채점 성능과 전체 요청의 실패율을 함께 제시한다.

동일 사례를 짝지어 비교한다. 같은 프로젝트에서 여러 질문을 만들었다면 프로젝트를 분석 단위로 묶어 불확실성을 계산한다. 반복 호출 수를 늘려 신뢰구간을 부당하게 좁히지 않는다. 확증 단계에서는 실무적으로 의미 있는 차이, 표본 수, 다중 비교 처리와 중단 규칙을 결과 조회 전에 확정한다. 탐색 자료로 유리한 기준을 정한 뒤 이를 사전 기준이라고 표현하지 않는다.

## 실제 사용자에게서 필요한 검증

먼저 대상 사용자 5~8명을 모집해 시작·완료·이탈, 질문 이해, 피드백 오해와 접근성 문제를 관찰한다. 이 규모는 초기 사용성 발견용이며 학습 효과의 통계적 입증 규모가 아니다.

학습 효과 비교는 별도다. 비슷한 출발 지식의 사용자를 코드핏과 일반 AI 도움 조건에 무작위 배정하고 같은 시간과 주제를 제공한다. 직접 배운 문제를 다시 푸는 점수보다 **새 상황에서 도움 없이 해결한 과제**를 주 지표로 삼고, 일정 시간이 지난 후 유지도 확인한다. 답안을 조건을 모르는 외부 평가자가 채점한다. 본 실험 규모는 파일럿 변동성과 목표 차이로 계산하고, 동의·철회·익명화·보관 기한을 모집 전에 확정한다.

사용자가 현재 평가자와 참여자를 모집하기 어렵다고 확인했다. 따라서 이 부분은 실행하지 않았고 SOTA 입증 판정을 유보한다. 사용자 대신 AI 에이전트를 넣은 시뮬레이션을 실제 학습 효과로 보고하지 않는다.

## 허용하는 설명

현재 사용 가능한 표현은 '원문 참조 방식으로 인용 오류를 줄였고, 자체 12개 회귀 사례를 두 번 통과했다'다. 독립 평가와 동등한 경쟁 구성의 비교가 완료되면 그 과제, 모델, 날짜, 평가 집합에 한정해 우수성을 설명할 수 있다. 그 결과만으로 서비스 전체의 SOTA를 선언하지 않는다.

## 제품 신뢰성 고도화 — 2026-09-19

평가 근거와 맞춤 실습이 장기간의 사용에서도 이어지도록 기록 탐색과 계정 복구를 보완했다. 프로젝트 기록을 20개씩 계속 읽고, 목록 밖의 평가도 본인 계정의 직접 링크로 열 수 있다. 새로고침·뒤로 가기·계정 전환에서 선택과 초안을 관리하고, 실패 재시도와 명시적인 새 분석을 구분한다. 모바일에서는 기록을 선택한 뒤 목록을 접는다.

이는 제품 사용성과 데이터 접근의 개선이며 모델 정확도나 학습 효과가 향상됐다는 근거가 아니다. 독립 평가와 실제 사용자 실험이 아직 없다는 위 판정은 그대로다. 구현과 검증 범위는 [프로젝트 점검](project-check.md#학습-기록-탐색과-계정-복구--2026-09-19)과 [검증 기록](VERIFICATION.md)에 남긴다.

2026-09-19 후속 구현에서 백업 v3의 공통 크기·개수 제한과 입문·프로젝트 학습 복원을 추가했다. [백업 계약](workspace-backup.md)과 실제 AI 결과의 복원 검증은 제품 신뢰성 근거이며, 독립 평가를 대체하지 않는다. 평가 준비가 가능해지면 위 독립 평가 계획에 따라 미공개 사례와 동등한 비교 조건을 고정한다. 현재 자체 사례를 추가 실행하는 것만으로 독립 검증을 대체하지 않는다.
