# 학습 기록 백업과 복원

2026-10-15 기준. 환경 설정의 **내 학습 기록 내보내기**는 작은 기록에는 기존 v3 JSON을, 용량이나 기록 수가 많은 계정에는 여러 v3 조각을 담은 v4 JSON 파일 하나를 만든다. 기존 v2 코딩 백업도 계속 가져올 수 있다. 백업 파일은 사용자가 수정할 수 있는 개인 기록이며 AI 판정이나 학습 성과의 진위를 인증하는 자료가 아니다.

## 포함 범위

- 본인이 진도나 풀이 기록을 남긴 문제, 본인이 생성한 문제, 이전 백업에서 가져온 문제. 전체 공개 문제 은행은 포함하지 않는다.
- 저장된 코드와 북마크, 힌트·정답 확인 상태, 제출 이력과 기존 보관 자료.
- 서버에 저장된 입문 실습 기록. 복원 시 미션과 기록의 형식·완료 조건을 검증한다.
- 완료된 프로젝트 분석, 수집한 공개 페이지 텍스트와 주소, 화면 이미지, 설명, 제출한 답변과 평가. 보완 회차의 직전 평가와 직접 작성한 확인 기록도 포함한다. 화면 이미지도 제거하지 않고 프로젝트와 같은 조각에 보관한다.
- 분석에 저장된 코드 읽기 추천(`codeGuide`)의 제목과 원본 인용. 추천 필드가 없는 이전 분석도 가져올 수 있으며 복원 시 Jev를 다시 호출하지 않는다.
- 프로젝트 클래스의 이름, 학습 목표와 메타데이터 리비전. 별도의 수업 복사본이 아니라 기존 프로젝트 분석에 포함된다.
- 프로젝트 학습의 최초 답변, 자신감과 도움 사용 기록, 고정된 문항·정답·해설 스냅샷. 복원 시 문항 해시와 점수의 일관성을 검증한다.

프로젝트 복습의 브라우저 메모·위치·선택·충돌 메모, 프로젝트 검색어, 보안 점검의 탭 임시 주소·결과·메모, 작업 공간 선택, 브라우저에만 남은 미저장 코드·미제출 답변, 실행 중인 AI 요청, 로그인 세션·인증 정보, 사용량 제한과 호출 로그는 포함하지 않는다. 파일에는 비공개 답변과 원문이 있으므로 다운로드 범위를 설정 화면과 개인정보 안내에도 표시한다.

생성된 프로젝트 코드 훈련과 서비스 동작 실습, 선택한 예상 답변, 저장한 확인 기록과 완료 상태도 프로젝트 묶음에 포함한다. 복원할 때 코드 인용과 단계 순서, 보기 범위를 검증한다. 프로젝트 AI 활용 학습의 주제, 코드 근거, 연결 수업, 확인 문제 답변과 적용 기록도 포함하며 복원 시 근거와 선택 범위를 검증한다. 기본 AI 실무 수업의 브라우저 진도는 이 백업에 포함하지 않는다.

## 일관성과 복원 정책

SQLite는 트랜잭션, PostgreSQL은 읽기 전용 repeatable-read 트랜잭션에서 백업을 읽는다. 가져오기 전에 새 학습 기록의 문항·참조·점수 관계와 코딩 진도·제출이 가리키는 문제와 검토 기준을 검증하며, 이 검증에 실패한 파일은 가져오기 횟수를 차감하지 않는다. 저장소 오류는 파일 불일치(400)가 아닌 서버 오류(500)로 알린다. 단일 v2/v3 파일 또는 v4 묶음의 각 조각은 코딩 기록부터 프로젝트 평가까지 하나의 트랜잭션으로 삽입한다. 마지막 평가 저장에서 실패를 주입해 해당 조각 전체의 롤백을 확인한다. 묶음 전체를 하나의 트랜잭션으로 처리하지는 않는다. 뒤 조각이 실패하면 앞서 완료한 조각은 유지하며, 화면에 실패 위치를 표시한다. 같은 파일을 다시 선택하면 기존 기록을 유지하며 남은 기록을 추가한다.

기존 코딩 진도, 입문 실습과 프로젝트는 덮어쓰지 않는다. 프로젝트는 분석과 평가·학습을 한 묶음으로 취급하므로 기존 분석만 있는 경우도 부분 병합하지 않는다. 반복 가져오기에서 동일 제출·프로젝트를 중복 생성하지 않는다. 다른 계정으로 가져온 프로젝트는 대상 계정과 원본 ID에서 파생한 새 UUID로 연결하며, 원본 계정의 직접 링크는 새 계정의 기록을 노출하지 않는다. 새 입문 실습과 코드는 대상 저장소의 리비전을 발급한다.

새로 가져온 문제의 계정 연결을 `restored_problems`에 보관한다. 진도 없이 보관한 문제도 재내보내기와 SQLite→PostgreSQL 이관에서 유지한다. 서비스에 없던 문제는 가져온 계정에만 보이도록 `problems.owner`와 `problem_catalog.owner`에 소유자를 기록한다. 다른 계정의 문제 목록, 통계, 추천과 직접 링크에는 나타나지 않으며, 파일의 출처 값과 관계없이 AI 문제로 표시하고 미래의 생성 시각은 가져온 시각으로 낮춘다. 이미 있는 기본·공개 문제의 ID는 기존처럼 연결만 하며 내용은 수정하지 않는다. 이 변경 전에 가져온 문제는 소유자를 구분할 수 없어 공개 상태로 남는다. 가져온 파일의 서술·점수가 실제 AI 생성 결과라는 진위는 보증하지 않는다.

## 공통 한도

각 HTTP 요청·응답의 앱 한도는 UTF-8 **4,000,000바이트 (4 MB)**로 유지한다. 기존 v2/v3 파일은 문제 2,500개, 풀이 10,000개, 입문 실습 500개, 프로젝트 500개까지다. 일반 내보내기가 크기 또는 개수 한도에 도달하면 클라이언트가 자동으로 조각 전송으로 전환한다.

v4 묶음의 각 v3 조각은 3,700,000바이트 이하이며, 묶음 식별자와 SHA-256 목록을 더해도 4 MB 안에서 전송한다. 최대 1,000개 조각을 파일 하나에 담는다. 코딩 풀이가 다른 조각으로 나뉘면 참조하는 문제 정의를 함께 포함하고, 프로젝트의 평가·이미지·학습 기록은 한 조각에 유지한다. 개별 기록 하나가 조각 한도를 넘는 이전 버전 원본은 별도 이관이 필요하며 전체 내보내기를 명시적으로 거절한다. 기록을 잘라내거나 일부만 성공으로 내려받지 않는다.

각 분할 내보내기 요청은 전체 계정 기록을 일관된 DB 스냅샷으로 다시 읽는다. 동일한 내보내기 시각과 전체 조각 해시를 비교해 수집 중 기록이 바뀌면 409로 중단한다. 최종 파일은 모든 조각을 받은 뒤 생성하므로 혼합 시점의 파일이 만들어지지 않는다. 이 방식은 별도 서버 파일 저장 없이 동작하지만 조각 수에 비례해 DB 읽기와 해시 계산을 반복한다. 로그인 계정 범위도 모든 요청에 고정한다.

가져오기 전 브라우저에서 조각 수·형식·전체 해시를 확인한다. 서버에서도 각 요청의 해시와 기존 문항·참조 검증을 반복한다. 해시는 손상을 찾는 장치이며 파일 작성자나 학습 성과를 인증하지 않는다.

가져오기는 계정당 24시간 5회, 접속망당 10회로 제한한다. v4는 조각 수와 관계없이 동일 묶음에 1회를 적용한다. 사용량 차감과 묶음 영수증, 조각 복원은 같은 트랜잭션에서 처리하므로 동시에 재시도해도 횟수가 중복 차감되지 않는다. 24시간 안에 같은 파일을 재시도하면 앞선 기록을 덮어쓰지 않는다. 조각은 별도로 계정당 5,000회, 전체 100,000회/24시간의 요청 상한과 문제·풀이 수 상한을 적용한다. 문제·풀이 수는 실제로 새로 삽입한 기록만 차감하므로 같은 파일의 앞부분을 재전송해도 남은 복원 분량의 한도를 소모하지 않는다. 신뢰할 수 있는 접속 IP가 없는 자체 호스팅(Vercel 외)에서는 모든 방문자가 한 접속망으로 묶이지 않도록 접속망 한도를 적용하지 않는다. 서비스 전체 한도(24시간 1,000회, 새 문제 250,000개, 풀이 1,000,000개)는 폭주만 막는 상한이며 한 사람이 모두 소진하기 어렵게 크게 두었다. 한도에 걸린 요청은 429로 거절하며 해당 조각의 기록 삽입과 한도 차감을 모두 되돌린다. 이전의 새 문제 100개 제한 때문에 정상 백업을 가져올 수 없던 경우를 수정했다. Vercel Functions의 요청·응답 4.5 MB 제한 안에서 오류 메시지까지 전달할 수 있도록 앱 한도를 4 MB로 둔다. v4 묶음은 파일 전체가 4 MB를 넘어도 각 조각을 순서대로 전송한다. 이전 로컬 버전에서 만든 4 MB 초과 단일 v2/v3 파일은 기존 설치에서 새 v4 묶음으로 내보내거나 별도 이관해야 한다. 가져오기 전 기존 문제 확인은 ID 500개씩 묶어서 조회하며 최대 5회다.

## 검증

v4 회귀 검사는 SQLite와 PostgreSQL의 공유 저장 계약, HTTP 요청, 클라이언트 검증에 둔다. 501개 프로젝트의 무누락, 이미지 보존, 손상 거절, 재시도 중복 방지와 한도 초과 시 롤백을 확인한다. Chromium에서는 다운로드→계정 전환→가져오기→프로젝트 재조회와 대용량 복원 중단→같은 파일 재시도를 확인한다. 일반 CI와 수동 전체 브라우저 검사의 범위는 [핵심 흐름 검증](critical-flow-verification.md)을 따른다. 이전 검증 이력은 [검증 기록](VERIFICATION.md)에 남아 있다.

`node --import tsx scripts/verify-project-recovery-live.ts`는 호출 계획만 출력한다. `--live`는 합성 프로젝트 페이지와 답변으로 실제 분석·평가 2회를 수행한다. 페이지 수집은 고정 합성 스냅샷을 사용하고 모델 응답은 대체하지 않는다. 두 독립 SQLite DB에서 저장·복원, 최초 답변과 문항 기준, 계정 격리와 추가 유료 호출 없는 재시도를 확인한다. 호출별 모델·비용 추정·지연과 입력·소스 해시를 보고서에 남기고 중단 시 재시도하지 않는다.

이 검사는 제품 신뢰성에 관한 것이며 전문가와의 채점 일치도, 사용자 학습 효과나 SOTA 순위를 입증하지 않는다.
